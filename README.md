---

## 🧠 My engineering approach

I try to keep one principle at the center:

**Solve the right problem before optimizing the implementation.**

### 01 · Understand

Identify the user, the business objective, the constraints, and the failure modes before reaching for a library.

### 02 · Design

Create clear boundaries between UI, state, data, and business logic. Prefer simple abstractions that can evolve with the product.

### 03 · Build

Treat loading states, validation, permissions, errors, empty states, accessibility, responsiveness, and edge cases as part of the feature.

### 04 · Ship

Software is not finished when it works locally.

It is finished when people can **use it, trust it, and maintain it**.

# 🎯 How I work

I don't need every implementation detail handed to me.

Give me a product problem and I can work backwards:

```text
Problem
   ↓
Constraints
   ↓
User experience
   ↓
Architecture
   ↓
Implementation
   ↓
Edge cases
   ↓
Testing
   ↓
Shipping
```

I'm comfortable moving between **product and engineering**:

**Product**

> What should the user experience be?

**Engineering**

> What architecture allows us to deliver that experience without creating unnecessary complexity?

That intersection is where I do my best work.
